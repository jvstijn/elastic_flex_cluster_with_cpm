## 2. Watcher: extensie achter elke topicnaam

Keuze: de extensie komt **uit het `cpm-pipeline-templates` document**, niet uit
Jinja in de watcher. Zelfde patroon als `kafka_bootstrap_dhl` dat er al in staat.
Voordeel: runtime aanpasbaar met een `PUT` zonder de watchers opnieuw uit te
rollen, en de inventory blijft leidend omdat `seed_data.yml` het veld elke run
opnieuw zet.

Vijf plekken in `watcher_cpm-pipeline-manager.json.j2`:

1. `String topicExt = '';` naast de bootstrap-defaults
2. + 3. uitlezen bij het dedicated én het catchall template
4. dedicated: `String topic = ... + namespace + topicExt;`
5. catchall: `if (!topicExt.isEmpty() && !t.endsWith(topicExt)) { t = t + topicExt; }`

Die `endsWith`-check zit er omdat een state-entry een expliciet `topic`-veld mag
hebben; zonder de check zou een al gesuffixte naam `-acc-acc` worden.

De extensie zit **alleen op het Kafka-topic**, niet op `data_stream_dataset` —
`logs-nginx-prod-acc` landt dus in de data stream `logs-nginx-prod` op een
acc-cluster. Dat is bewust: anders zouden de dashboards en ML-jobs in acc op
andere streamnamen moeten kijken.

Gerenderd met dummy-variabelen en door `json.loads` gehaald: de watcher-JSON
blijft geldig.

`elastic_cpm_workflows` is niet aangepast — dat is de parallelle variant die niet
draait.

## 3. Topics aanmaken en vullen

`create_kafka_topics.py` leest de topics tot nu toe uit de Logstash-pipelines.
Voor acc moet de bron Kafka zelf zijn ("alles wat er nu staat"), dus twee vlaggen
erbij:

```bash
python3 scripts/create_kafka_topics.py --source kafka --suffix=-acc --dry-run
python3 scripts/create_kafka_topics.py --source kafka --suffix=-acc
```

Namen die al op de suffix eindigen worden overgeslagen, dus herhalen levert nooit
`...-acc-acc`. `--source logstash` blijft de default; bestaand gebruik verandert
niet.

`fill_kafka_events.py` kreeg `--only-suffix=-acc`, zodat het vullen van acc de
productie-topics met rust laat. De `prefer`-lijst voor de big topics krijgt de
suffix mee, anders vielen die terug op willekeurige topics.

Let op de schrijfwijze: `--suffix=-acc` met een `=`. Zonder het isgelijkteken
leest argparse `-acc` als een optienaam en stopt met een foutmelding. Stond
eerst overal fout in de documentatie.

**`scripts/gen_stream_data.py` (nieuw).** De bestaande scripts dekten het
genereren van echte testdata niet: `fill_kafka_events.py` produceert willekeurige
bytes met `kafka-producer-perf-test.sh` (goed voor volume, niet parseerbaar als
JSON) en `seed_test_dataset.py` leest juist bestaande streams uit monitoring. Het
nieuwe script maakt per dataset x namespace echte JSON-documenten met een
`data_stream`-object en produceert die rechtstreeks in het doeltopic — dus
zonder de router op `test-dataset`, wat nodig is omdat die de `-acc` extensie
niet kent.

```bash
python3 scripts/gen_stream_data.py --ensure-topics --count 1250 --hours 24
python3 scripts/gen_stream_data.py --suffix=-acc --count 1250 --hours 24
```

## 5. Namespace-conventie: default / ns1 / ns2 / ns3

Alle testdata is opnieuw opgezet met vier namespaces. De zes datasets (nginx,
nginx.access, webapp, firewall, application.auditd, en metrics/system) x vier
namespaces = 24 topics per omgeving.

Opgeruimd in Kafka: de zes `-prod` / `-tst` topics verwijderd. De state-entries
met die namespaces zijn uit `cpm-pipeline-state` gehaald.

De bijbehorende **data streams in Elasticsearch zijn blijven staan** (3.000 docs
op de prd-clusters). Om te voorkomen dat CPM ze via monitoring opnieuw ontdekt en
pipelines bouwt voor topics die niet meer bestaan, staan ze nu als exclusion:

```
*-prod   namespace-conventie 27-08: alleen default/ns1/ns2/ns3
*-tst    namespace-conventie 27-08: alleen default/ns1/ns2/ns3
```

Willen we ze echt weg, dan is dat een `_delete_by_query` per cluster.

**Kip-ei bij nieuwe streams.** CPM ontdekt data streams via stack monitoring
(`.ds-logs-*` in `.monitoring-es-8-*`), niet via Kafka. Een nieuw topic alleen is
dus niet genoeg: geen stream → geen state → geen pipeline → nooit een stream.
Daarom zijn de 24 streams per omgeving gebootstrapt met 20 documenten direct in
ES, verdeeld over de drie clusters. Daarna neemt de keten het over vanuit Kafka.

wijziging. Resultaat: twee groups van elk 96 leden, allebei lag 0.

> **De topic-extensie alleen is niet genoeg.** Die scheidt de namen, niet de

## 7. Scheve startverdeling voor de routing-advisor

Een gelijke verdeling geeft de advisor niets te doen, dus de testdata is opnieuw
opgezet met een bewuste onbalans: 16 / 5 / 3 streams en 24.000 / 4.500 / 1.500
events.

| | central | remote-a | remote-b |
|---|---|---|---|
| streams | 16 | 5 | 3 |
| events | 24.000 | 4.500 | 1.500 |
| datasets | nginx, nginx.access, webapp, firewall | application.auditd + metrics-system-default | metrics-system ns1/ns2/ns3 |

**Wat hierbij misging en waarom.** Eerste poging: streams scheef bootstrappen in
ES en dan de cyclus draaien. Dat werkt niet, om twee redenen:

1. De **state-manager neemt de bootstraplocatie niet over** — hij verdeelt zelf
   op basis van de clusterscores. De 16/5/3 werd binnen één cyclus 10/9/3.
2. De data was al geproduceerd toen de nieuwe pipelines er nog niet waren, dus de
   events liepen door de pipelines van de vórige ronde. Resultaat: 11.7k / 10.9k
   / 10.9k, vrijwel gelijk.

De werkende volgorde is dus:

```
data streams weg  ->  state direct scheef schrijven  ->  ALLEEN pipeline-manager
  ->  data genereren  ->  (later) volledige cyclus = rechttrekken
```

De state-manager mag er tussendoor niet overheen, anders is de onbalans meteen
verdwenen. `scripts/gen_stream_data.py` kreeg `--only-topics` zodat een groep
streams een ander volume kan krijgen dan een andere.

**Nulmeting** (voordat de advisor eroverheen gaat):

| | central | remote-a | remote-b |
|---|---|---|---|
| PRD | 25.000 (75,8%) | 5.500 (16,7%) | 2.500 (7,6%) |
| ACC | 24.000 (80,0%) | 4.500 (15,0%) | 1.500 (5,0%) |

Rechttrekken doe je met een volledige cyclus:

```bash
python3 scripts/cpm_run_now.py --insecure                               # prd
python3 scripts/cpm_run_now.py --host https://localhost:9210 --insecure  # acc
```

Dat de advisor daadwerkelijk ingrijpt is al gezien bij een veel kleinere
onbalans: drie suggesties op prd met bron/doel-scores (20,70 -> 19,88), plus
promotie van drie zware streams naar dedicated pipelines.

## 8. Downgrade naar 9.4.1

Elasticsearch kent **geen downgrade**: een node die op 9.4.2 heeft gedraaid
weigert te starten op 9.4.1 (`cannot downgrade a node from version [9.4.2] to
version [9.4.1]`). `STACK_VERSION` aanpassen is dus niet genoeg — de
data-volumes moeten weg.

Aanpak: beide stacks afgebroken en de ES/Kibana-volumes verwijderd, maar
**Kafka bewust laten draaien**. Die hangt niet aan `STACK_VERSION`
(`apache/kafka:3.9.0`), dus alle topics en hun inhoud bleven staan; alleen de
Elasticsearch-kant is opnieuw opgebouwd.

Omdat de consumer-offsets daardoor nog op het einde van de vorige ronde stonden,
is er nieuwe data geproduceerd in plaats van de offsets te resetten — de topics
bevatten inmiddels meerdere rondes cumulatief, dus `earliest` zou een
onvoorspelbaar aantal opleveren.

Twee dingen die bij de herbouw stukgingen en nu structureel opgelost zijn:

**a. `cpm_logstash` + ingest-keys ontbraken in docker-local.** Dit was de vierde
handmatige herbouwstap die sinds 18-08 openstond. De user en de API-keys bestaan
alleen runtime in ES en verdwenen met de volumes; de prd-Logstash stopte met
`unable to authenticate user [cpm_logstash]` -> FATAL en er kwam niets binnen.
`docker-local/setup/init-stack.sh` doet nu hetzelfde als de acc-variant: rol,
user, ingest-key per cluster en die keys terugschrijven in `.env`. De
init-mount is daarvoor van `:ro` naar rw gezet.

**b. `active: true` ontbrak in de local-inventory.** Bij een verse registry komt
elk cluster op `active: false` binnen. Zonder die regel had prd na de herbouw
stilgestaan — dezelfde val als eerder bij acc. Staat nu in beide inventories.

De Kibana-plugin moest opnieuw geïnstalleerd worden (zie sectie 9).

## 10. Waarom er geen dedicated pipelines waren

Langste zoektocht van vandaag, en het antwoord lag niet bij CPM maar bij de
**vorm van de testdata**.

De routing-advisor werkt op een gemeten event-rate. Die leidt hij af uit de
*groei* van `elasticsearch.index.total.indexing.index_total` tussen twee
uurbuckets in stack monitoring:

```painless
if (tb.size() >= 2) { ... if (diff > 0.0) delta = (long)diff; }
if (rate <= 0L) continue;          // geen groei -> geen kandidaat
```

En een dedicated pipeline ontstaat **uitsluitend** uit zo'n suggestie; in de
state-manager staat letterlijk `// ====== DEDICATED PIPELINES (from routing
suggestions) ======`. De keten is:

```
scoring -> routing-advisor (schrijft suggestie) -> state-manager
  (zet om in pipeline_type: dedicated) -> pipeline-manager (rendert)
```

Onze testdata was één burst: 30.000 events inladen en klaar. Daarna staat
`index_total` stil (1520 -> 1520 -> 1520), delta 0, elke stream valt af bij die
`continue`. De chain deed dus precies wat hij moest doen — er was niets te
adviseren. Zodra er verse events binnenkwamen ging het bucket naar 2320 en was
het meteen raak.

### Vijf voorwaarden

1. **Continue instroom, geen bulk load.** Vastgelegd in
   `scripts/simulate_continuous_load.py`: kleinere batches met tussenpozen, met
   bewust verschillende volumes per groep zodat de advisor kan rangschikken.
2. **Twee uurbuckets historie** binnen `now-2h`. Een vers cluster heeft er één.
3. **Metricbeat per cluster** — zonder `.monitoring-es-8-*` is er geen bron.
4. **Spreid de drukke streams over de clusters.** Dit was het lastigst. De
   advisor neemt de top-N streams op rate, waarbij `int N = scoreMap.size()`
   (= aantal clusters), en gebruikt elk doelcluster één keer
   (`usedTargets`). Staan alle drukke streams op één cluster, dan krijgt alleen
   dat cluster een dedicated: de rest valt af op `if (tgtScore < srcScore)`,
   want naar een zwaarder cluster verplaatst hij niet. Op acc lukte het in één
   keer omdat de scores daar vrijwel gelijk waren (20,25 alom → de
   "score ties prefer source"-tak levert een local dedicated per cluster). Op
   prd was central het lichtst (19,93 tegen 20,24 en 20,28) én droeg het de
   zestien drukste streams — daar waren drie gerichte bursts nodig, één per
   cluster.
5. **Meerdere cycli.** Per run komen er hooguit #clusters dedicated pipelines
   bij.

## 11. Logstash OOM bij een catchall met veel topics

`logstash-central` viel om met `java.lang.OutOfMemoryError: Java heap space` en
daarna kwam er in prd niets meer binnen. Oorzaak: een catchall-pipeline met 16
topics draait `consumer_threads: 16` maal twee Kafka-inputs, en dat past niet in
de 256m heap uit de compose.

Alle zes CPM-Logstash-instanties staan nu op `-Xms768m -Xmx768m` met
`mem_limit: 1610612736` (1,5g). Aandachtspunt voor elke omgeving waar een
cluster veel topics bundelt.
