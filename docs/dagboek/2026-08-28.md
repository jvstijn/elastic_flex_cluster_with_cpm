De ERROR-regels in de Logstash-logs waren vals alarm: `grep -i error` matcht op
de JVM-vlag `HeapDumpOnOutOfMemoryError` in de opstartregel.

### Pipelines liepen één cyclus achter op de state

Opgemerkt bij het controleren, nog niet rechtgezet:

| cluster | `cpm-pipeline-state` | uitgerolde pipeline |
|---|---|---|
| acc-central | logs-firewall-ns3 | logs-firewall-default-acc |
| acc-a | logs-firewall-default | logs-webapp-default-acc |
| acc-b | logs-webapp-default | logs-firewall-ns2-acc |

De uitgerolde set is precies de toewijzing van de vorige cyclus. Gevolg is dat
`logs-firewall-ns3-acc` zowel in de catchall staat als volgens state dedicated is
op acc-central, wat dubbele ingest oplevert zolang dat zo blijft. Eén ronde
`scripts/cpm_run_now.py --host https://localhost:9210 --insecure` trekt het recht.

Nog uit te zoeken of dit een echte race is (state-manager schrijft zonder
refresh, pipeline-manager leest de vorige versie) of alleen een momentopname van
een afgebroken cyclus bij het afsluiten gisteren.

## 2. CPM-plugin zit nu in het image

Structurele oplossing voor §9 van 27-08. Nieuw bestand
`kibana_plugin/Dockerfile.install`:

```dockerfile
ARG STACK_VERSION=9.4.1
FROM docker.elastic.co/kibana/kibana:${STACK_VERSION}
ARG STACK_VERSION
USER root
COPY build/cpm-${STACK_VERSION}.zip /tmp/cpm.zip
RUN bin/kibana-plugin install "file:///tmp/cpm.zip" \
  && rm -f /tmp/cpm.zip \
  && chown -R kibana:root plugins
USER kibana
```

Het verschil met de bestaande `Dockerfile` is wezenlijk. Die kloont
`elastic/kibana`, draait `yarn kbn bootstrap` en compileert de plugin — een image
van ruim 20 GB dat netwerk nodig heeft. `Dockerfile.install` pakt alleen de al
gebouwde zip uit `build/` uit en is in 0,4 seconde klaar. Daarmee is dit ook de
route voor de air-gapped installatie: alleen het officiële Kibana-image en de
zip zijn nodig.

In beide compose-bestanden is de `image:`-regel van de kibana-service vervangen
door:

```yaml
    build:
      context: ../kibana_plugin
      dockerfile: Dockerfile.install
      args:
        STACK_VERSION: ${STACK_VERSION}
    image: cpm-kibana:${STACK_VERSION}
```

`build:` naast `image:` betekent: bouwen als het image nog niet bestaat, en
taggen als `cpm-kibana:<versie>`. Vanaf nu levert `docker compose up -d` dus
altijd een Kibana mét plugin.

### Valkuil: .dockerignore sloot de zip uit

`kibana_plugin/.dockerignore` had `build` in de lijst — logisch voor de
compileer-Dockerfile, waar `build/` juist de uitvoer is, maar fataal voor
`Dockerfile.install`, die de zip nodig heeft. Opgelost met een uitzondering:

```
build
!build/*.zip
```

### Versiekoppeling

De zip moet exact bij `STACK_VERSION` passen; Kibana weigert een plugin waarvan
`kibanaVersion` afwijkt. In `build/` staan nu `cpm-9.4.1.zip` en
`cpm-9.4.2.zip`. Bij een versiebump zonder bijbehorende zip faalt de build op de
`COPY`. Nieuwe zip bouwen gaat met
`KIBANA_VERSION=<versie> ./scripts/build_kibana_cpm_plugin.sh`.

Compose bouwt niet opnieuw als het image al bestaat, dus na het vervangen van een
zip is `--build` nodig:

```bash
docker compose -f docker-local/docker-compose.yml up -d --build kibana
docker compose -f docker-acc/docker-compose.yml  up -d --build kibana
```

### Gecontroleerd

```bash
docker exec dod-elastic-kibana-1     ls plugins   # -> cpm
docker exec dod-elastic-acc-kibana-1 ls plugins   # -> cpm
```

Beide Kibana's melden `status: available` met de plugin geladen, en de API van
de plugin antwoordt op beide poorten. Let op dat een losse curl naar
`/api/cpm/clusters` een 400 geeft met *"exists but is not available with the
current configuration"*; dat is geen fout in de plugin maar Kibana die de
internal-origin header mist:

```bash
curl -s -u elastic:$PW -H 'kbn-xsrf: true' -H 'x-elastic-internal-origin: Kibana' \
    http://localhost:5602/api/cpm/clusters
```

Levert de drie acc-clusters, alle drie `active: true`.

## 3. Apart monitoring-cluster per omgeving

Aanleiding was de vraag hoe de weging tot stand komt. Het antwoord: centraal.
Elke Metricbeat scrapet zijn eigen cluster maar schreef naar es-central, dus
`.monitoring-es-8-*` stond op hetzelfde cluster als de watchers. De
cross-cluster alias `monitoring:` wees terug naar es-central zelf. In de
air-gapped omgeving staat monitoring op een eigen cluster, dus die vlieger gaat
daar niet op. Nu wel gelijkgetrokken, met een monitoring-cluster per omgeving.

| | docker-local | docker-acc |
|---|---|---|
| monitoring-cluster | es-monitoring | es-acc-monitoring |
| poort | 9203 | 9213 |
| cluster.name | monitoring-cluster | acc-monitoring-cluster |
| alias vanaf central | `monitoring:` | `monitoring:` |

Het nieuwe cluster heeft bewust **geen** `node.attr.dc`, en er staat ook geen
Metricbeat op gericht. Daardoor komt het niet in `.monitoring-es-8-*` terecht,
ziet registry-sync het niet, en blijft de registry op precies drie
data-clusters staan. Nagerekend: drie clusters in de registry, alle drie actief.

### De ML-datafeeds liepen niet mee

Dit was de val die ik gisteren al vermoedde en die vandaag echt toesloeg. De
watchers hebben `monitoring:.monitoring-es-8-*` hard in hun templates staan, maar
de ML-datafeeds bouwen hun index op uit `cpm_monitoring_index`, en die stond op
het kale `.monitoring-es-8-*`. Zolang monitoring op es-central zelf stond viel
het verschil niet op. Met een apart cluster zoeken de datafeeds lokaal, vinden
ze niets en blijven alle scores op 0.

De variabele staat nu op `monitoring:.monitoring-es-8-*`, in de defaults en in de
inventories van local en acc. De template `cpm_monitoring_search_url.j2` gebruikt
hem nu ook echt in plaats van een `{% raw %}`-literal. De kaposi-inventory is
bewust ongewijzigd gelaten, met een comment: daar staat monitoring nog op
es-central-01.

Let op de volgorde bij het omzetten. Een draaiende datafeed leest niet met
terugwerkende kracht, dus na het verhuizen van de monitoring-data moet de ML een
keer opnieuw:

```bash
.venv/bin/ansible-playbook -i inventories/local/hosts site.yml -e cpm_ml_reinstall=true
```

### Keystore van es-central overleefde het niet

Halverwege stonden alle drie de remotes ineens op `connected: false`, ook
remote_a en remote_b die niets met deze wijziging te maken hadden. De foutmelding
was duidelijk genoeg:

```
Cross cluster requests through the dedicated remote cluster server port require
transport header [_cross_cluster_access_credentials] but none found.
```

De cross-cluster credentials staan in de keystore van es-central, en die staat in
de containerlaag, niet op een volume. Zodra de container opnieuw wordt aangemaakt
zijn ze weg. En dat gebeurt sneller dan je denkt: `init` schrijft nieuwe
ingest-keys terug in `.env`, alle es-services hebben `env_file: .env`, dus compose
ziet een gewijzigde config en maakt ze opnieuw aan. Gevolg: CCS dood, CPM blind,
zonder dat er iets aan CPM zelf mankeert.

`init-stack.sh` is daarom herschikt. Wachten, trial en een nieuwe functie
`ensure_ccs_credentials` staan nu **voor** de marker-check en draaien dus bij
elke start. De sleutels zelf worden hergebruikt uit
`/setup/state/ccs-keys.env` op het init-state volume, zodat er niet bij iedere
herstart een API-key bijkomt. Alleen het echte eenmalige werk (wachtwoorden,
users, ingest-keys, bootstrap-pipeline) zit nog achter de marker.

### Historie meeverhuizen

Een leeg monitoring-cluster betekent geen historie, en zonder historie geen
model, geen forecast en dus scores van 0. Nieuw script
`scripts/copy_monitoring_history.py` scrollt `.monitoring-es-8-*` van het oude
naar het nieuwe cluster en schrijft met op_type `create` en behoud van `_id`, dus
opnieuw draaien levert geen duplicaten op (status 409 telt als geslaagd).

```bash
ELASTIC_PASSWORD=... python3 scripts/copy_monitoring_history.py --since now-6h
ELASTIC_PASSWORD=... python3 scripts/copy_monitoring_history.py \
    --src https://localhost:9210 --dst https://localhost:9213 --since now-6h
```

Zes uur historie is ongeveer 200.000 documenten per omgeving, in een minuut of
vijftien. Dat is meer dan het lijkt omdat Metricbeat elke 10 seconden meet.
Hetzelfde script is bruikbaar bij de omzetting in de air-gapped omgeving.

### Oude monitoring-data opgeruimd

Na de omschakeling bleef op es-central en es-acc-central de oude data stream
`.monitoring-es-8-mb` achter. Niemand schreef er nog naartoe en niemand las hem
nog: het laatste document dateerde exact van het moment van omschakelen en er
kwam in tien minuten niets bij. Samen ruim 700 MB.

```bash
curl -sk -u elastic:$PW -X DELETE https://localhost:9200/_data_stream/.monitoring-es-8-mb
curl -sk -u elastic:$PW -X DELETE https://localhost:9210/_data_stream/.monitoring-es-8-mb
```

| cluster | voor | na |
|---|---|---|
| es-central | 484.987 docs, 345 MB | leeg |
| es-acc-central | 511.233 docs, 369 MB | leeg |

Na anderhalve minuut kwam de index niet terug, dus er schrijft echt niets meer.
De keten daarna nog een ronde gedraaid: alle zes de watchers doen het.

Het indextemplate `.monitoring-es-mb` staat er nog, dus mocht er ooit weer
lokaal naartoe geschreven worden, dan ontstaat de data stream netjes opnieuw.
Wat weg is, is de historie ouder dan de zes uur die naar het monitoring-cluster
is gekopieerd.
