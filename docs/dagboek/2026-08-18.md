## 1. Exclusion bestond al — geen nieuwe code

Index `cpm-stream-exclusions` (mapping in `ansible/roles/elastic_cpm/files/json/`,
aangemaakt via `defaults/main.yml:41`), veld `topic_pattern` met wildcard-steun.
Gelezen door drie watchers: `cpm-state-manager`, `cpm-routing-advisor` en
`cpm-stream-coverage`. Gedocumenteerd in `docs/runbook-stream-routing.md` sectie B.

De state-manager past de check toe op **zeven** plaatsen; elke `stateEntries.add`
wordt voorafgegaan door een exclusion-check:

| Regel | Sectie | Beschermt |
|---|---|---|
| 75 | Routing locks | `stateEntries.add` (123) |
| 138 | Dedicated uit routing suggestions | `stateEntries.add` (191) |
| 215 | Bestaande state | `stateEntries.add` (296) + `stateDeletions` (237) |
| 398 | Discovery uit monitoring | voedt de merge |
| 506 | Catchall state entries | `stateEntries.add` (561) |
| 597, 638 | Opruiming | achtergebleven state + routing suggestions |

**Gat:** de workflow-variant `cpmw-state-manager.yml` heeft *geen enkele*
exclusion-logica. Draai je die in plaats van de watchers, dan werkt excluden niet.
Wij draaien de watchers, dus geen actie — wel iets om te weten.

## 3. Wipe en herbouw

`docker compose down -v` (9 volumes) + `up -d`. Nieuwe trial actief tot **17-09**,
`watcher` en `logstash` weer `available=True`. Nieuwe cluster-UUID's.

Vier stappen die de wipe stukmaakt en die **niet** geautomatiseerd zijn:

1. **Ingest-API-keys** — `VAR_API_KEY_CENTRAL/_REMOTE_A/_REMOTE_B` in `.env`.
   `init-stack.sh` maakt alleen de *CCS*-keys. Zonder regeneratie: 401 op alle
   Logstash-outputs. Rol-privilege let op: `auto_configure` is een **index**-privilege,
   niet een cluster-privilege (400 bij aanmaken).
2. **`cpm_logstash`-user + rol `cpm_logstash_pipelines`** — bestaan alleen runtime in
   ES-security (zie dagboek 17-07), niet in de repo. Zonder deze user crashen alle
   drie de Logstash-instanties bij het opstarten op
   `unable to authenticate user [cpm_logstash]` → `LicenseError` → `FATAL`, en ze
   herstarten niet vanzelf. Rol = cluster-privileges `monitor` +
   `manage_logstash_pipelines`, user-wachtwoord = `LOGSTASH_PASSWORD`.
3. **`active: true` in `cpm-cluster-registry`** — registry-sync zet nieuwe clusters op
   `active: false`. De state-manager slaat inactieve clusters over, dus de eerste
   CPM-run gaf `index_state=condition_failed` en 0 pipelines. Was al bekend als
   openstaand punt; nu bevestigd als harde blokkade bij elke verse omgeving.
4. **Ansible-venv** — `ansible-playbook` stond niet op PATH; `./scripts/setup_local.sh`
   maakt hem. `requests` ontbrak voor de seed-scripts en is bijgeïnstalleerd.

Verder: de seed-scripts hebben `--ca-cert` nodig (CA uit
`es-central:/usr/share/elasticsearch/config/certs/ca/ca.crt`), anders
`CERTIFICATE_VERIFY_FAILED`.

## 4. Twee bugs gevonden

### a. `create_kafka_topics.py` sloeg het laatste topic over — GEREPAREERD
`"\n".join(topics)` levert geen afsluitende newline, en de shell-lus
`while IFS= read -r t` verwerkt de laatste regel dan niet. Van 8 topics werden er 7
aangemaakt; `test-dataset` (alfabetisch laatst) ontbrak stilzwijgend. De melding
"topics now in the cluster: 8" verhulde het, want die telt `__consumer_offsets` mee.

Dit werd pas schadelijk door de wijziging van 13-08: mét auto-create maakte de broker
`test-dataset` alsnog aan. `test-dataset` is het input-topic van de router.

Fix: `input=("\n".join(topics) + "\n").encode()`. Daarna `created/exists: 8 failed: 0`.

### b. `cpm_run_now.py` roept een niet-bestaande watcher aan — NIET gerepareerd
Het script draait `cpm-register-sync`, maar de watcher heet `cpm-registry-sync`.
Gevolg: `!! cpm-register-sync: http 404` bij elke run. De overige vijf stappen
draaien wel, dus het is geen blokkade — maar de registry-sync wordt dus nooit
uitgevoerd door dit script.

### Test 4 — filebeat-scenario (klassieke index `filebeat-8.15.0` op remote-a)
Bevestigd, live:

| | Waarde |
|---|---|
| State-document `_id` | `logs-filebeat-default` |
| State-veld `topic` | `filebeat` |
| Logstash-input dc-a | `logs-filebeat-default` |
| Output-tak keyt op | `[@metadata][kafka][topic] == "filebeat"` |

De state-manager schrijft `topic: "filebeat"` met `data_stream_type: "logs"` (de
default blijft staan omdat `filebeat` geen streepje bevat). De pipeline-manager ziet
een topic dat niet met `logs-`/`metrics-`/`traces-` begint en herschrijft hem naar
`logs-filebeat-default`.

**Gevolg:** de filebeat-outputtak — index `filebeat-%{[agent][version]}` met
`action => "create"` en `pipeline => "%{[@metadata][pipeline]}"` — is **dode code**;
hij kan nooit matchen. Filebeat-data belandt in de `else`-tak als data stream
`logs-filebeat-default`. Geen dataverlies, wel ander gedrag dan bedoeld.

De keten is intern consistent (`create_kafka_topics.py` maakt óók
`logs-filebeat-default` aan), dus dit valt alleen op als je de outputtak verwacht te
zien werken.

### Bijvangst: `delete_excluded_suggestions=failure` is loos alarm
De watcher probeert routing-suggestions te verwijderen die niet bestaan; de webhook
telt een 404 `not_found` als failure. Functioneel klopt alles.
